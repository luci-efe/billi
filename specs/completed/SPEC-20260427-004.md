# SPEC-20260427-004: Document Management & Evidence

**Stage:** QA
**Created:** 2026-04-27
**Updated:** 2026-04-27
**Author:** Gemini CLI

## Purpose

Provide a secure and efficient way to link physical evidence (receipts, invoices, documents) to financial transactions, ensuring that users can retrieve and view evidence for tax or accounting purposes.

## Scope

### In Scope
- Linking PDF/Image documents to existing transactions.
- Storage infrastructure using Cloudflare R2.
- Document retrieval and gallery view in `apps/web`.
- Basic search and filtering of documents by transaction metadata.

### Out of Scope
- Automatic tax validation of invoices (e.g., XML SAT validation).
- Document editing or annotation.
- Public sharing of documents (limited to authenticated owner).

## Requirements

### REQ-001: Linking Evidence to Transactions
**Priority:** P0
**Description:** The system SHALL allow users to upload and associate a document (image/PDF) with a specific transaction record.

#### Acceptance Criteria
- **GIVEN** an existing transaction ID
  **WHEN** a user uploads a valid file
  **THEN** the system SHALL create a record in the `documents` table and associate it with the transaction.
- **GIVEN** a file upload request
  **WHEN** the file size exceeds 5MB
  **THEN** the system SHALL reject the upload and return a clear error message.

#### Scenarios
- **Happy path: Successful association**
  - Setup: A transaction with ID `tx_789` exists.
  - Action: User uploads `receipt.pdf` for `tx_789`.
  - Expected: File is stored in R2, and a document record links `tx_789` to the R2 key.
- **Edge case: Multiple documents**
  - Setup: A transaction already has one document.
  - Action: User uploads a second image for the same transaction.
  - Expected: Both documents are associated with the transaction and visible in the UI.
- **Error case: Invalid file type**
  - Setup: User attempts to upload an `.exe` file.
  - Action: Upload request is sent.
  - Expected: System returns error: "Formato de archivo no permitido. Solo se aceptan imágenes y PDFs."

### REQ-002: Evidence Storage with Cloudflare R2
**Priority:** P0
**Description:** The system SHALL store all uploaded documents in Cloudflare R2 for durability and scalability.

#### Acceptance Criteria
- **GIVEN** a valid file buffer
  **WHEN** saving to storage
  **THEN** the system MUST use a unique, cryptographically secure key (e.g., ULID) to prevent URL guessing.
- **GIVEN** a request to view a document
  **WHEN** authorized
  **THEN** the system SHALL return a temporary signed URL for secure access.

#### Scenarios
- **Happy path: Secure storage**
  - Setup: Server receive a 2MB image.
  - Action: Server uploads to `billi-documents` bucket.
  - Expected: File is successfully put into R2 with a path like `user_123/tx_789/01JK...pdf`.
- **Edge case: Re-uploading same file**
  - Setup: User uploads `receipt.jpg` twice.
  - Action: Two separate upload events occur.
  - Expected: System stores them as distinct objects with unique keys to avoid collisions.
- **Error case: R2 Authorization failure**
  - Setup: R2 bucket credentials are misconfigured.
  - Action: User attempts upload.
  - Expected: System logs a critical error and informs user: "Error de conexión con el servidor de archivos."

### REQ-003: Document Retrieval & Viewing
**Priority:** P1
**Description:** The system SHALL provide a dedicated view for users to browse, search, and view their uploaded documents.

#### Acceptance Criteria
- **GIVEN** a user viewing their transaction history
  **WHEN** a transaction has an associated document
  **THEN** an evidence icon SHALL be visible.
- **GIVEN** a clicked evidence icon
  **WHEN** the document is fetched
  **THEN** the system SHALL display the document in a Modal viewer using the `Dialog` component.

#### Scenarios
- **Happy path: Document Preview**
  - Setup: User is in the Transactions list.
  - Action: User clicks the "Ver comprobante" button.
  - Expected: A Dialog opens showing the image or PDF preview.
- **Edge case: Missing file in R2**
  - Setup: DB record exists but R2 object was manually deleted.
  - Action: User attempts to view.
  - Expected: System shows a "Archivo no encontrado" state within the Dialog.
- **Error case: Unauthorized access attempt**
  - Setup: User A tries to guess User B's document URL.
  - Action: User A requests document metadata for a `doc_id` they don't own.
  - Expected: API returns 403 Forbidden or 404 Not Found.

## Technical Approach

### Architecture
- **Schema:** Create `packages/db/src/schema/documents.ts` with `id`, `ownerId`, `transactionId`, `storageKey`, `fileName`, `fileType`, `fileSize`.
- **API:** 
  - `POST /api/documents/upload`: Multipart/form-data handler using Cloudflare R2 bindings.
  - `GET /api/documents/:id`: Returns metadata and a signed URL (via `getSignedUrl` from AWS SDK).
- **Frontend:**
  - `apps/web/src/components/documents/DocumentViewer.tsx`: Uses the existing `Dialog` component.
  - `apps/web/src/components/documents/FileUpload.tsx`: Progress-aware upload component.

### Key Decisions
- **R2 Native API:** Use the Cloudflare Workers R2 API (via bindings) instead of the S3 compatibility layer for better performance and integration within the worker.
- **ULID Keys:** Use ULIDs for both DB IDs and R2 keys to maintain sortability and non-guessability.
