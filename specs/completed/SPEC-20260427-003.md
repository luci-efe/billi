# SPEC-20260427-003: Smart Multi-modal Capture

**ID:** SPEC-20260427-003
**Name:** smart-multimodal-capture
**Stage:** QA
**Created:** 2026-04-27
**Updated:** 2026-04-27
**Author:** Gemini CLI

## Purpose

Streamline transaction registration through natural language and OCR-based capture, allowing users to record financial data quickly and accurately with minimal manual effort.

## Scope

### In Scope
- Natural language transaction registration (text input).
- OCR-based registration from receipt images.
- Intermediate "Proposal" state for verification.
- Entity extraction (amount, date, category, merchant).

### Out of Scope
- Automatic confirmation without user review.
- Processing of bank statements (deferred).
- Multi-currency conversion during capture (uses default).

## Requirements

### REQ-001: Natural Language Interpretation
**Priority:** P0
**Description:** The system SHALL interpret free-form text to extract transaction entities and present an editable proposal.

#### Acceptance Criteria
- **GIVEN** a natural language phrase from the user
  **WHEN** processed by the extraction pipeline
  **THEN** the system SHALL return a structured object with `amountCents`, `category`, `type`, and `date`.

#### Scenarios
- **Happy path: Clear intent**
  - Setup: User is in the chat interface.
  - Action: User enters "Spent 150 on gas today".
  - Expected: A proposal is shown with 150.00 MXN, category 'Transporte', type 'expense', and today's date.
- **Edge case: Ambiguous category**
  - Setup: User enters "Paid 200 at OXXO".
  - Action: System processes the message.
  - Expected: A proposal is shown with a suggested category (e.g., 'Gastos Hormiga' or 'Varios') and a note "Merchant: OXXO".
- **Error case: Unintelligible input**
  - Setup: User enters "random gibberish".
  - Action: System processes the message.
  - Expected: System SHALL inform the user that it couldn't understand the transaction details and ask for clarification.

### REQ-002: OCR Receipt Processing
**Priority:** P0
**Description:** The system SHALL extract financial data from images of receipts or invoices using OCR and Vision LLMs.

#### Acceptance Criteria
- **GIVEN** an uploaded receipt image
  **WHEN** processed by the multimodal extraction pipeline
  **THEN** it SHALL extract the total amount, date, and suggested category from the visual data.

#### Scenarios
- **Happy path: High-quality receipt**
  - Setup: User uploads a clear photo of a Walmart receipt.
  - Action: Vision LLM processes the image.
  - Expected: A proposal is generated with the correct total, date, and category 'Supermercado'.
- **Edge case: Handwritten receipt**
  - Setup: User uploads a photo of a handwritten nota de remisión.
  - Action: Vision LLM processes the image.
  - Expected: System attempts extraction; if confident scores are low, it presents a partial proposal and highlights fields for review.
- **Error case: Unreadable image**
  - Setup: User uploads a completely blurry image.
  - Action: Vision LLM processes the image.
  - Expected: System informs the user: "No pudimos leer el recibo. ¿Quieres intentarlo de nuevo o capturarlo manualmente?".

### REQ-003: Editable Capture Proposals
**Priority:** P1
**Description:** The system MUST present all extracted data as an editable proposal before any persistence occurs.

#### Acceptance Criteria
- **GIVEN** an extracted transaction proposal
  **WHEN** displayed to the user
  **THEN** the user SHALL be able to modify any field (amount, category, date, note) before confirming.

#### Scenarios
- **Happy path: User confirms proposal**
  - Setup: Proposal is shown on screen.
  - Action: User reviews and clicks "Confirmar".
  - Expected: Transaction is saved to the database and a success feedback is shown.
- **Edge case: User cancels proposal**
  - Setup: Proposal is shown on screen.
  - Action: User clicks "Cancelar".
  - Expected: Proposal is discarded, no database record is created.
- **Error case: Submission failure**
  - Setup: User clicks "Confirmar" but the network is down.
  - Action: Frontend attempts to save.
  - Expected: System SHALL show an error message and keep the proposal state so the user can retry.

## Technical Approach

### Architecture
- **Mastra Workflow (`apps/api/src/mastra/workflows/capture.ts`):** 
  - `ExtractionStep`: Uses Claude 3.5 Sonnet (vision-capable) to process text or image.
  - `RefinementStep`: Maps extracted text categories to internal category IDs.
- **Storage:** 
  - Temporary files stored in Cloudflare R2 (bucket: `billi-captures`).
  - Metadata stored in `transactions` table with `source = 'image'` and `source_ref` pointing to R2 key.
- **Frontend (`apps/web/src/components/chat/ProposalCard.tsx`):**
  - New component to display and edit transaction proposals.

### Key Decisions
- **Unified Extraction:** Use the same LLM (Claude 3.5 Sonnet) for both text and OCR to maintain consistency in entity extraction.
- **Explicit Review:** ALWAYS require user confirmation to prevent accidental or incorrect entries.
