# SPEC-20260426-007: Advanced Transaction Management

**ID:** SPEC-20260426-007
**Name:** advanced-transaction-management
**Stage:** TEST
**Created:** 2026-04-26
**Updated:** 2026-04-26
**Author:** Gemini CLI

## Purpose

Enable users to efficiently manage large volumes of financial data through bulk operations, advanced filtering, and enhanced UI interactions, reducing manual effort in transaction organization.

## Scope

### In Scope
- Multi-select capability in the transaction table.
- Bulk delete functionality.
- Bulk update capability (specifically for categories).
- Advanced filtering UI (amount ranges, source filters).
- Backend support for bulk operations in Hono.

### Out of Scope
- External data synchronization (Plaid, bank APIs).
- Automatic transaction matching/reconciliation.
- Undo functionality (to be considered for a future spec).

## Requirements

### REQ-001: Multi-Select Transaction Table
**Priority:** P0
**Description:** The system SHALL allow the user to select multiple transactions using checkboxes in the transaction list.

#### Acceptance Criteria
- **GIVEN** a list of transactions **WHEN** the user clicks the header checkbox **THEN** all visible transactions are selected.
- **GIVEN** selected transactions **WHEN** the user navigates away or clears filters **THEN** the selection SHALL be cleared to prevent accidental operations on non-visible data.
- **GIVEN** a mix of selected and unselected transactions **WHEN** the header checkbox is clicked **THEN** it SHALL toggle between "select all" and "select none".

#### Scenarios
- **Happy path: Selection Persistence**
  - Setup: User is on the transactions page with 10 items.
  - Action: User selects 3 items manually.
  - Expected: The selection count displays "3 items selected" and the floating action bar appears.
- **Edge case: Select All across pages**
  - Setup: User has 50 transactions across 5 pages.
  - Action: User clicks "Select all visible" and then "Select all 50 items".
  - Expected: System tracks selection of all 50 IDs.
- **Error case: Selection during Refresh**
  - Setup: User has 5 items selected.
  - Action: List is refreshed and selected items are no longer in the result set.
  - Expected: Selection SHALL be cleared.

### REQ-002: Bulk Delete Operations
**Priority:** P0
**Description:** The system SHALL provide a way to delete all selected transactions in a single request.

#### Acceptance Criteria
- **GIVEN** multiple selected transactions **WHEN** the user confirms deletion in the confirmation dialog **THEN** the system MUST call the bulk delete endpoint and refresh the list.
- **GIVEN** no transactions are selected **WHEN** viewing the transactions page **THEN** the bulk delete action MUST be disabled or hidden.

#### Scenarios
- **Happy path: Successful Bulk Delete**
  - Setup: 5 transactions selected.
  - Action: User clicks "Delete" and confirms in dialog.
  - Expected: API called with 5 IDs, items removed from UI, success toast shown.
- **Edge case: Deleting all items on a page**
  - Setup: User selects all 10 items on page 1.
  - Action: User deletes items.
  - Expected: UI should automatically navigate to the previous page or show empty state if no items remain.
- **Error case: Partial Failure**
  - Setup: 3 items selected, one item is restricted/invalid.
  - Action: Bulk delete triggered.
  - Expected: System MUST use a database transaction to ensure atomicity OR report which items failed if atomicity is not possible.

### REQ-003: Bulk Category Update
**Priority:** P1
**Description:** The system SHALL allow the user to change the category of multiple selected transactions simultaneously.

#### Acceptance Criteria
- **GIVEN** selected transactions **WHEN** the user selects a new category from a bulk update menu **THEN** all selected transactions SHALL be updated to that category in the database.
- **GIVEN** transactions with different existing categories **WHEN** updated to a new category **THEN** all SHALL converge to the new selection.

#### Scenarios
- **Happy path: Successful Re-categorization**
  - Setup: 10 transactions with category "Uncategorized".
  - Action: User selects all and chooses "Dining" category.
  - Expected: All 10 transactions now show "Dining" as their category.
- **Edge case: Update to same category**
  - Setup: 5 transactions already in "Groceries".
  - Action: User updates them to "Groceries".
  - Expected: No database changes should be triggered (idempotent) or handled gracefully by DB.
- **Error case: Invalid Category Selection**
  - Setup: Bulk update triggered.
  - Action: Backend receives a non-existent category ID.
  - Expected: Error message displayed to user, no transactions updated.

## Technical Approach

### Architecture
- **Database (PostgreSQL/Drizzle):** Update `packages/db/src/repos/transactions.ts` to include `deleteTransactions(ids: string[])` and `updateTransactionsCategory(ids: string[], categoryId: string)`. Use `db.delete().where(inArray(transactions.id, ids))` for efficient batch processing.
- **API (Hono):** Implement `POST /transactions/bulk-delete` and `PATCH /transactions/bulk-category` endpoints.
- **Frontend (React/TanStack Table):** 
  - Enable `rowSelection` in the `useReactTable` hook.
  - Implement a `SelectionBar` component that appears when `table.getSelectedRowModel().rows.length > 0`.
  - Use Shadcn UI `Checkbox` for row selection and `DropdownMenu` or `Command` for bulk category selection.

### Key Decisions
- **Atomicity:** Bulk operations MUST be wrapped in a database transaction to prevent partial states.
- **Selection State:** Use internal table state for selection rather than syncing to global state (URL/Redux) unless multi-page "select all" is required.

### Dependencies
- `@tanstack/react-table` for selection logic.
- `lucide-react` for icons in the floating action bar.
