# SPEC-20260426-005: Transaction Management & Export

**ID:** SPEC-20260426-005
**Name:** transaction-management-export
**Stage:** QA
**Created:** 2026-04-26
**Updated:** 2026-04-26
**Author:** Gemini CLI

## Purpose

Provide a robust transaction list view with advanced filtering and the ability to export data to CSV for external usage, addressing the "Exportación CSV" requirements in BIL-18.

## Scope

### In Scope
- Development of a detailed Transaction List component with pagination using shadcn/ui.
- Server-side filtering by date range, transaction type, and category using Drizzle ORM.
- Generation of a CSV file on the server and downloading it on the client.
- Integration with the main dashboard.

### Out of Scope
- PDF report generation (reserved for Premium/BIL-20).
- Advanced charts (handled in the Analytics spec).
- Bulk editing of transactions (future enhancement).

## Requirements

### REQ-001: Transaction List View
**Priority:** P0
**Description:** The system SHALL display a list of all transactions belonging to the authenticated user in a structured table.

#### Acceptance Criteria
- **GIVEN** an authenticated user with transactions
  **WHEN** they navigate to the transactions page
  **THEN** the system SHALL display a table with columns for: Date, Description, Category, Type (Income/Expense), and Amount.
- **GIVEN** a large number of transactions
  **WHEN** the list is loaded
  **THEN** the system SHALL support server-side pagination to limit the initial payload.

#### Scenarios
- **Happy Path: List loads successfully**
  - Setup: User has 5 transactions in the database.
  - Action: Navigate to /transactions.
  - Expected: 5 rows are displayed with correct data.
- **Edge Case: No transactions found**
  - Setup: User has 0 transactions.
  - Action: Navigate to /transactions.
  - Expected: Table displays an empty state message "No transactions found."
- **Error Case: API failure**
  - Setup: The backend service is down.
  - Action: Navigate to /transactions.
  - Expected: An error message is displayed to the user: "Failed to load transactions."

### REQ-002: CSV Export Implementation
**Priority:** P0
**Description:** The system SHALL allow the user to download their filtered transaction data in CSV format.

#### Acceptance Criteria
- **GIVEN** a set of filtered or unfiltered transactions
  **WHEN** the user clicks the "Export CSV" button
  **THEN** the system SHALL generate a CSV file on the server and trigger a download in the browser.
- **GIVEN** the exported CSV file
  **WHEN** opened
  **THEN** it SHALL contain headers for all table columns and matching transaction records.

#### Scenarios
- **Happy Path: Successful export**
  - Setup: User has 10 transactions.
  - Action: Click "Export CSV".
  - Expected: Browser downloads `transactions_export_[timestamp].csv` with 11 lines (1 header + 10 data).
- **Edge Case: Exporting empty filter result**
  - Setup: User filters for a date range with 0 transactions.
  - Action: Click "Export CSV".
  - Expected: CSV is downloaded with only the header row OR a message indicating no data to export.
- **Error Case: Generation failure**
  - Setup: Server fails to process the export request.
  - Action: Click "Export CSV".
  - Expected: Error toast is displayed: "Failed to generate export."

### REQ-003: Advanced Filtering
**Priority:** P1
**Description:** The system SHALL allow users to filter transactions by date range and category.

#### Acceptance Criteria
- **GIVEN** the transaction list
  **WHEN** a user selects a Category filter
  **THEN** the list SHALL refresh to show only transactions of that category.
- **GIVEN** the transaction list
  **WHEN** a user selects a Date Range (Start/End)
  **THEN** the list SHALL refresh to show transactions within that inclusive range.

#### Scenarios
- **Happy Path: Combined filtering**
  - Setup: User has multiple categories and dates.
  - Action: Filter by "Food" and date "2026-04-01 to 2026-04-30".
  - Expected: List shows only Food transactions in April.
- **Edge Case: Invalid date range**
  - Setup: User sets End Date earlier than Start Date.
  - Action: Apply filter.
  - Expected: Validation error or automatic correction.
- **Error Case: Filter timeout**
  - Setup: Query takes too long to execute.
  - Action: Apply filters.
  - Expected: Loading state followed by graceful error handling.

## Technical Approach

### Architecture
- **Frontend:**
  - `TransactionList` component in `apps/web/src/components/transactions/transaction-list.tsx`.
  - Uses `@shadcn/ui` `Table`, `Pagination`, and `Data-Table` components.
  - State management for filters and pagination via URL search params (to support sharing/refreshing).
- **Backend:**
  - Hono API endpoint `GET /api/transactions` in `apps/api/src/routes/transactions.ts`.
  - Uses Drizzle ORM to build dynamic queries based on query parameters (`category`, `startDate`, `endDate`, `page`, `limit`).
- **Export Utility:**
  - Server-side CSV generation using a streaming approach or a library like `json2csv`.
  - Endpoint `GET /api/transactions/export` accepts same filters as the list endpoint.

### Key Decisions
- **Decision:** Server-side filtering.
  - **Rationale:** Ensures performance as the transaction history grows and keeps export logic consistent.
- **Decision:** URL-based filtering state.
  - **Rationale:** Improves UX by allowing users to bookmark or share specific filtered views.
- **Decision:** shadcn/ui Table.
  - **Rationale:** Consistent design system and robust accessibility features.

### Dependencies
- `@shadcn/ui` (Table, Button, Calendar, Select)
- `drizzle-orm`
- `lucide-react` (Icons)
- `date-fns` (Date manipulation)
