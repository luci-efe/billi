## Purpose

Enhance the current dashboard with visual analytics, including category spending breakdowns and trend comparison, to help users understand their financial habits (Addressing BIL-11).

## Scope

### In Scope
- Visual representation of spending by category using charts (e.g., Donut or Bar chart).
- Comparison of current period income/expenses against the previous period (Trend Analysis).
- Interactive dashboard widgets that update based on the selected period.

### Out of Scope
- Deep historical analysis beyond a 2-period comparison (Premium/BIL-12).
- Goal tracking or budgeting (future epics).

## Requirements

### REQ-001: Spending by Category Chart
**Priority:** P0
**Description:** The system SHALL display a visual breakdown of expenses grouped by category for the selected period.

#### Acceptance Criteria
- **GIVEN** a user with transactions in multiple categories for the selected period
  **WHEN** they view the dashboard analytics section
  **THEN** the system SHALL render a Recharts Donut chart displaying the proportional spending for each category.

#### Scenarios
- **Happy path: Multiple categories**
  - Setup: 3 categories with varying expense totals.
  - Action: User views the dashboard for the current month.
  - Expected: Donut chart renders with 3 segments representing the correct percentages.
- **Edge case: Single category**
  - Setup: Only 1 category has expenses.
  - Action: User views the dashboard.
  - Expected: Donut chart renders as a solid circle representing 100% of the single category.
- **Error case: No data for period**
  - Setup: No transactions in the selected period.
  - Action: User views the dashboard.
  - Expected: "No spending data available for this period" message is displayed instead of a blank chart.

### REQ-002: Month-over-Month Trend Comparison
**Priority:** P1
**Description:** The system SHALL calculate and display the percentage difference for income and expenses between the current period and the immediate previous period.

#### Acceptance Criteria
- **GIVEN** transactions in the current and previous month
  **WHEN** the user views the summary widgets
  **THEN** the system SHALL display a delta indicator (e.g., +15%) with appropriate color coding (red for increased expenses, green for increased income).

#### Scenarios
- **Happy path: Expense increase**
  - Setup: Prev month expenses: $1000, Current month expenses: $1200.
  - Action: User views the dashboard.
  - Expected: Expense delta shows "+20%" in red.
- **Edge case: Previous month zero**
  - Setup: Prev month expenses: $0, Current month expenses: $500.
  - Action: User views the dashboard.
  - Expected: Delta shows "New activity" or handled without division-by-zero errors.
- **Error case: Database timeout**
  - Setup: Database fails to respond to aggregation query.
  - Action: User views the dashboard.
  - Expected: Summary widgets show a graceful error state or "-" instead of crashing the UI.

### REQ-003: Interactive Period Selection
**Priority:** P1
**Description:** The system SHALL provide a period selector (e.g., Current Month, Last 30 Days, Year-to-Date) that filters all dashboard analytics.

#### Acceptance Criteria
- **GIVEN** a dashboard with analytics widgets
  **WHEN** the user selects "Last 30 Days" from the period selector
  **THEN** the system SHALL re-calculate and refresh all charts and summary deltas to reflect the new date range.

#### Scenarios
- **Happy path: Change period**
  - Setup: Dashboard viewing "Current Month".
  - Action: User selects "Last 30 Days".
  - Expected: Widgets update data immediately with a loading state.
- **Edge case: Future date ranges**
  - Setup: System date is May 1st, user tries to select "Next Month".
  - Action: Selector interaction.
  - Expected: Future ranges should be disabled or show zero data correctly.
- **Error case: Invalid period parameter**
  - Setup: URL manipulated to an invalid period string.
  - Action: Page load.
  - Expected: System reverts to "Current Month" as a safe fallback.

## Technical Approach

### Architecture
- **Backend:** New API routes in `apps/api/src/routes/analytics.ts` for aggregated data.
- **Database:** Use Drizzle `groupBy` and aggregation functions (e.g., `sum(amount)`) in `packages/db`.
- **Frontend:** Recharts components in `apps/web/src/components/dashboard/analytics/` utilizing shadcn/ui charts.

### Key Decisions
- **Server-side Aggregation:** All financial calculations (sums, percentages) SHALL be performed in the database/API layer to minimize payload size and improve mobile performance.
- **MoM Logic:** Percentage deltas SHALL be calculated on the server to ensure consistency across web and future mobile clients.
- **Chart Library:** Recharts SHALL be used for its declarative nature and compatibility with shadcn/ui styling.

### Dependencies
- `recharts`: For rendering SVG charts.
- `lucide-react`: For trend indicators (ArrowUp/ArrowDown icons).

### Risks
- **Query Performance:** Large datasets may slow down aggregation.
  - *Mitigation:* Ensure indexes on `createdAt`, `userId`, and `type` in the transactions table.

## Test Strategy
